# Go-to-market inicial — CISPAR Agent

## Mensaje central

El landing debe transmitir que una amenaza, una alerta o una tarea de coding puede avanzar mientras el equipo espera. CISPAR debe presentarse como una forma de actuar con más rapidez y control.

## Mensaje editorial

La sección de incidentes debe usar casos reales y fuentes públicas. Cada tarjeta responde:

1. Qué ocurrió.
2. Qué impacto tuvo.
3. Qué señal o retraso importó.
4. Qué habría que detectar o automatizar.
5. En qué punto CISPAR ayuda.

Ejemplo de tono:

> Una vulnerabilidad no espera a que tu equipo tenga tiempo. Detecta antes de perder datos, continuidad y confianza.

El copy puede ser urgente, pero no debe afirmar que una empresa habría evitado un incidente por usar CISPAR sin evidencia.

## Funnel

```text
Incidente verificable → explicación clara → demo/captura → descarga → login → primera tarea → suscripción
```

## CTAs

- Principal: “Descarga CISPAR”.
- Para quien todavía evalúa: “Mira cómo responde a un incidente”.
- Para conversión: “Prueba tu primera tarea”.
- Para cuentas pagadas: “Abrir CISPAR”.

## Contenido mínimo

- Tres incidentes o análisis verificables como máximo en la portada.
- Archivo `/incidents` para el contenido completo.
- Fuente, fecha, autor o equipo editorial y fecha de revisión.
- Corrección visible si una fuente cambia.

## Lo que se evita

- Miedo sin datos.
- Logos de clientes sin permiso.
- Métricas inventadas.
- Claims de compliance no certificados.
- Login obligatorio antes de entender el producto.
